# Kelivo 与 Codex 远控：统一 Kelivo 风格与双独立功能方案

日期：2026-11-04，验收延续至 2026-11-05。状态：现有远控首轮 Kelivo 视觉迁移已实施并隔离验证；完整 AI 整合仍为候选，未构建或发布新 APK。详见[本轮记录](../audits/2026-11-04/kelivo-style.md)。

## 1. 为什么调整路线

用户只有自己与 Codex 协作，希望更快在一个 Android App 中使用 Kelivo 式 AI 和现有电脑 Codex 远控。

2026-11-03 的方案以模块移植和全量对照为主要规划单位，20–34 人周及 10–16 周带有两名开发、半职测试的前提，不能直接作为当前协作方式的日历交付承诺。用户之后明确：电脑执行阶段直接进入现有远控界面，无需手机 AI 持续转述或协调。这使小范围二次开发成为更合适的优先路线。

用户在本轮进一步明确：**整个 App 必须统一为 Kelivo 风格；AI 助手与电脑远控必须各自独立使用；“交给电脑”只是额外联动，不能成为使用远控的必经流程。**此前以保留两套界面换取速度的前提已被用户否决。

当前方案：**以 Kelivo 为统一视觉基准，沿用其 AI 界面与完整功能实现；将电脑远控的导航、页面、输入和设置适配为同一套风格；提供两个同级独立入口，另加可选交接。**尽量复用现有远控通信、状态与原生插件，减少业务逻辑改写。

Flutter 主程序与 Capacitor 远控的组合仍是技术候选，需验证能否满足统一导航、主题、返回及状态恢复；不能仅因两个页面能打开，就认定达到产品目标。最终功能范围继续按用户原先的一比一目标规划，界面则服从本轮明确的 Kelivo 统一设计要求。

## 2. 已确认的产品决定

1. 手机 AI 直接连接用户选择的模型服务，日常聊天不依赖 Mac 在线；这里不要求手机离线运行大模型。
2. AI 助手与电脑远控各自可直接使用。打开远控不需要先与 AI 聊天、生成任务卡或调用手机模型；AI 助手不因 Mac 离线或远控未配对而被阻断。
3. 交接内容是确认的任务说明和必要附件，包含目标、约束、验收要求；不默认转发完整手机聊天。
4. 项目和 Codex 会话由用户在同一张确认卡中选择，支持新建或继续已有会话是用户要求，不能静默删除。
5. 可选交接中，用户选择项目、会话并确认后进入同一 App 的电脑远控区，直接与电脑 Codex 沟通，保留原发送、进度、审批、排队、停止能力；远控界面按 Kelivo 风格调整。
6. 执行阶段不安排手机模型逐条转述、监督或总结 Codex 输出，因此不为该中转过程额外发模型请求。
7. 已授权任务范围内自动推进；新任务和范围变化仍遵守确认规则，不能因切换界面获得无限执行授权。
8. 用户明确选择 B：统一为 Kelivo 风格。统一导航、字体、配色、图标、间距、圆角、输入框、消息与工具卡片、设置及浅深主题；不能把原 Kelivo 和原远控的两套风格并排保留作为首版交付。
9. 单纯切换功能不生成或提交任务、不自动交接上下文、不重发未知结果，也不等于停止电脑正在执行的任务。各自保留会话、草稿和阅读位置，回到功能区时按原运行时规则恢复。

尚待确认：是否接受先交付常用流程验收的 preview，再完成全部功能对照；首版也必须满足已覆盖页面的统一设计。默认落点与正式合并包的数据迁移策略属于实施前需落实的设计事项；任何功能范围缩减均需用户明确调整，不能由交付节奏推定。用户现已授权先迁移现有远控界面；本轮仅实施这一范围。AI 功能导入、双入口与交接尚未实施。

## 3. 产品结构与使用方式

~~~text
一个 App：统一 Kelivo 风格与导航
├─ AI 助手（独立入口）
│  ├─ 模型选择、独立聊天、Kelivo 工具与其他完整功能
│  └─ 可选“交给电脑”操作，准备任务说明与必要附件
├─ 电脑远控（独立入口）
│  ├─ 可直接选项目/会话，继续电脑 Codex
│  ├─ 消息、进度、审批、排队、停止等原有能力
│  └─ 也可接收 AI 助手交接草稿，确认后开始新电脑任务
└─ 设置（统一入口）
   ├─ 全局外观、主题与产品更新
   ├─ AI 模型/账号/工具配置
   └─ 电脑连接/配对/诊断配置
~~~

| 使用方式 | 入口与流程 | 依赖边界 |
| --- | --- | --- |
| 独立 AI 助手 | 打开 AI 助手，直接聊天和使用工具 | 不要求 Mac 在线或先配对远控；所选模型/工具的服务条件仍按原功能要求 |
| 独立电脑远控 | 打开电脑远控，选择或继续电脑会话 | 不要求配置或调用手机聊天模型；电脑及原连接链路仍需可用 |
| 可选交接 | AI 助手中选择任务说明/附件 → 选项目与会话 → 用户确认 → 电脑远控 | 只在用户主动发起时发生；确认前不提交 |

两个功能在产品导航中同级；底部标签或其他具体导航形态在设计样稿中确定，不把“AI → 交接 → 远控”设为唯一使用路线。共享设置入口按业务分组，不要求统一两套凭证或业务数据库。

“交给电脑”只是打开待确认草稿，不直接提交模型任务。确认动作位于远控端，使用其现有连接与控制状态；跨运行时交接不透传连接令牌，不把正文或密钥塞进 URL。

交接记录需有唯一 ID、状态和目标绑定。反复切页、重建或收到重复 Intent 时只恢复草稿或同一提交状态；取消不发送，未知接收结果不自动再提交。附件按用户选择交接，通过原附件上传路径送达电脑，不能只传手机文件路径并假定 Mac 能读取。

任务卡复用远控端现有目标状态与提交机制；具体由哪层渲染以统一界面验证结果决定，不为外观重写控制协议。每个交接的新电脑任务启动前由用户确认一次；打开草稿属于导航操作。直接使用远控时沿用原有操作与授权语义，不能因增加交接而强制所有远控消息都先经过手机 AI。

### 统一界面的验收条件

- 以固定版本 Kelivo 的真实界面为参考，整理字体、色值、间距、圆角、图标、触控目标、浅深主题及动态效果的对照，不能只改主题色。
- AI 助手沿用其界面基础；电脑远控的导航、消息、输入框、附件、工具与确认卡片按同一规范适配，保留审批/排队/停止等真实语义。
- 导航与设置入口一致，不出现重复顶栏、重复主导航或进入另一个完整 App 的体验；返回关系和系统返回键行为明确。
- 模型/账号/工具等深层设置及远控连接/诊断页面纳入设计对照，不能只统一两张首页截图。
- 切换功能保留各自会话、草稿及阅读位置；全局主题切换后两边同步。进程或连接恢复按原能力重新核验，不把隐藏页面当作任务已停止。
- 验收覆盖 AI/远控独立使用、可选交接、设置、浅深主题、键盘和常用屏宽；尚未统一的页面不能按成品通过。

### 保留的边界

- Kelivo 与远控的历史、配置、模型身份分别保留；不因界面统一而强制合并聊天历史或底层数据库。全 App 统一 Kelivo 风格已经纳入设计和实施范围。
- 复用现有六个原生插件及 Capacitor HTTP，维持凭证、录音、诊断、剪贴板和更新能力；普通浏览器 WebView 不能直接视为这些能力的替代品。
- 更新源必须属于合并产品，不能沿用上游更新后把合并包安装回原版 Kelivo。Flutter/原生改动通过完整 APK 更新；原 Web 热更新要校验兼容版本。
- 优先复用上游业务实现；改动范围包括统一设计下的导航、页面与组件，必要 Android 宿主适配及交接层。固定版本仍是 v1.3.4 对应提交，后续升级另行记录差异。
- 对目标用户直接覆盖原 codex-to-phone，还是先安装独立 preview，实施前根据签名和存储位置决定。独立包不会自动继承另一个包的 Keystore/缓存；不假定现有数据自动迁移。

## 4. 已核实的依据与实际障碍

### 4.1 支持这条路线的源码证据

| 证据 | 实际含义 |
| --- | --- |
| Kelivo 的 android/app/src/main/kotlin/com/psyche/kelivo/KelivoApplication.kt:12、19、29–36 | Application 持有后台、定时、工作区、设备工具及共享 Flutter Engine，保留主程序可少改这套所有权 |
| 本仓 apps/mobile/android/app/src/main/java/com/mobilecodex/app/MainActivity.java:8 | 原远控使用 BridgeActivity，注册六个插件，没有自己的 Application 子类声明 |
| Capacitor 7.6.9 BridgeActivity.java:11、22–25、42–47 | Bridge 与插件依附于 Activity；提供独立接入点，但 onCreate 会修改 Application 的主题，主题影响需要测试 |
| 本仓 apps/mobile/src/features/connection/http.ts:31、profiles.ts:5 | 原生 HTTP 与凭证插件是现有路径的一部分，不能仅复制网页就宣称能力完整 |
| 本仓 apps/mobile/src/app/App.tsx:852、881 | 已有 Desktop 消息发送、clientMessageId 和控制状态保护，交接应接入这些规则 |

Android 官方允许一个应用声明多个 Activity 并用显式 Intent 导航。这只是平台机制依据，不是该组合已经通过构建的证明。

同 APK 多 Activity 不能替代统一体验验收。技术验证需按 Kelivo 设计实现 AI/远控样例、全局导航与设置，验证主题、键盘、安全区、返回和状态恢复。若保留两个运行时达不到该条件，再比较嵌入方式或局部界面改写；不能退回保留两套风格来宣布完成，也不预设必须把全部 React 改写为 Dart。

### 4.2 “新建会话”是待解决的真实缺口

本仓 App.tsx:628 的新建按钮清理本地选择；:722 之后的提交逻辑在无已有 Desktop 会话时会走 /api/live/turns，随后可产生 source=appServer 的会话（约 :768–790）。因此，不能把当前“新建线程”直接当作已经具备创建并控制原 Codex Desktop 会话的能力。

用户选择的“新建或继续已有会话”应单独验收：先核对 Desktop/插件是否有可用的原生新建接口，再确定实现。能力不足时，交接到已有 Desktop 会话可以先做 preview，但这时必须明确新建项未完成；它仍保留在最终需求中，不能用 app-server 会话冒充 Desktop 原会话。该缺口可能影响首版工期，不能按简单页面拼接计算。

### 4.3 构建与设备条件

本轮只发现 flutter/dart/adb 未在当前 shell PATH 上；这不证明机器未安装，需在实施首步检查项目工具链及本地 SDK 路径。现有项目已有 APK 构建脚本，应复用其 JDK/Android SDK 记录，另准备与固定 Kelivo 版本兼容的 Flutter 工具链。

两边 Android Gradle、资源名、插件清单、CMake/JNI、Manifest、主题及更新入口尚未合并验证。不能基于“代码量小”承诺不会遇到原生兼容阻塞。

## 5. 交付节奏与排期修正

**此前“累计 5–10 个集中工作日拿到可用 preview”的目标依赖保留两套界面，不适用于本轮需求，现撤回该排期。**不能一边新增整体界面统一的工作，一边保留原先的小改动时间目标。

更快的手段是沿用 Kelivo 的成熟 AI 界面与功能，主要适配远控界面，减少业务逻辑重写。统一设计与两个独立入口均为交付条件。下面是候选工作顺序；是否分阶段交 preview 仍待用户确定。

| 阶段 | 可审查交付 | 完成条件 |
| --- | --- | --- |
| F0 统一设计与技术验证 | Kelivo 组件对照、AI 与远控样例、构建及兼容记录 | 同一设计下两个入口都可直接访问；主题/返回/插件基本正常；新建 Desktop 会话有核查结论 |
| F1 两个独立功能预览 | 统一界面的 AI 助手与电脑远控、全局设置、已验页面清单 | Mac 离线仍可用 AI；手机模型未配置仍可用远控；切换不提交任务、不串草稿，核心路径按同一设计验证 |
| F2 可选任务交接 | 任务说明/附件草稿、项目/会话选择与单次确认 | 不影响独立入口；取消不发、确认只发一次；内容到达正确目标；新建能力不足时明确未完成，不计全交接通过 |
| F3 固定版本全量验收与日常验证 | 原 59 组功能矩阵、统一界面覆盖及升级/恢复证据 | 完整功能目标和已约定页面均通过；缺失或受阻不能计完成；常用流程通过不代替全部供应商/系统能力验收 |

实施启动后可先为 F0 设 2–3 个集中工作日的研究时间盒，用来获得实际构建与统一界面集成证据；这不是保证 F0 在该时间内完成。后续周期待设计覆盖、实际兼容结果和剩余矩阵明确后再估，不以未经实测的新数字替换旧数字。**加快首次可用不能以保留两套风格或弱化完整功能目标为代价。**

## 6. 后续完整整合工作包（尚未启动）

前置视觉试迁移已完成：现有远控、Agent、设置及浅深主题采用 Kelivo 参考，通信和控制逻辑保持原实现。它只完成统一设计中的远控部分，不计 F0 原生整合通过。下一轮先做工作包 1–3，取得合并构建和生命周期证据后再推进 4–7。

1. 固定上游 tag、提交、依赖及原项目可用基线，盘点现有改动；不覆盖用户工作区，不操作线上网关。
2. 根据固定版本 Kelivo 的真实界面整理组件对照，形成 AI 助手、电脑远控及设置的一致设计样稿，列明深层页面覆盖。
3. 查明 Flutter/Android/JDK/NDK 路径，复现固定上游 Android release 构建，再验证保留原业务实现的宿主组合；以统一导航、主题、返回和状态恢复为门槛。
4. 在获准的实施范围内实现两个独立入口与统一设计，复用原远控通信/状态/六个原生插件，验证 Mac 离线和手机模型未配置两种独立使用场景。
5. 用合成任务、测试附件和本地假服务增加可选交接；确认前不得写入真实 Codex 任务；复用原 clientMessageId/未知结果保护。
6. 验证取消、重复 Intent、切页/后台、返回、进程恢复、凭证与附件权限，单独核查原 Codex Desktop 新建会话；不得以 app-server 会话代替。
7. 产出已统一界面的 preview、功能/视觉验收范围、已知问题与后续矩阵。涉及真实模型/控制的测试依项目规则单独安排，不夹带在隔离测试中。

首轮不主动重写 Kelivo 供应商或工具、不搬原数据库、不修改 Mac 端服务、不把两个模型串成持续转述链路。若项目的明确缺口需要修改协议或 Mac 接口，则先把该差异写入具体工作包。

## 7. 全量目标与许可条件

保留全量功能代码是降低遗漏的手段，合并后的完整功能可用性仍需验证。原 [功能矩阵](2026-11-03-kelivo-parity-matrix.md) 继续作为最终对照；此前 [可行性方案](2026-11-03-kelivo-parity-feasibility.md) 的固定版本、数据恢复与外部服务边界继续有效。

本轮明确“一比一”继续约束功能覆盖和行为，界面按统一 Kelivo 风格适配；不能借外观调整删去原功能、配置或权限提示。此前文档中的入口、视觉及排期前提如与本轮决定冲突，以本文为准。

源码复用仍需沿用此前的 AGPL/第三方依赖合规路径；更换主壳或提前交 preview 不会消除原许可要求。本文不新增法律结论，也不假定上游内置运营服务可以任意转为本产品配套服务。
