# 重复输入的完整过渡测试与修正方案

日期：2026-10-23。用户本轮要求“测试当前问题并给出方案”。本轮完成隔离测试和方案，没有修改产品源码、构建或发布APK；当前问题仍未修复。

## 测试结论

发现可稳定复现的消息过渡缺陷：服务端临时输入被正式输入替换后，手机仍保留旧投影及其身份关联，能够显示为“用户气泡—执行过程—相同用户气泡”。重复还会进入缓存，在重连或重新打开后保留。

该失败使用合成数据，经当前App实际更新函数、当前合并器、实际显示入口和真实React组件复现。它解释了截图所示排列的一种产生方式，但手机20:43截图的早期缺身份状态尚未取得，不能认定已证明该次截图的全部根因。

完整字段的最终态投影仍正常：此前真实只读native/history及确认占位的6种回放顺序均一份；本轮用独立合成数据在App入口复测这6种顺序也全部一份。旧12:32报告对应另一句输入，不替代20:43截图证据。

## 复现方法与结果

隔离脚本：`output/audit/2026-10-23/input-persistent-diagnosis/transition-test.mjs`。运行：

```sh
node output/audit/2026-10-23/input-persistent-diagnosis/transition-test.mjs
```

脚本通过TypeScript AST提取当前App内的`applyDesktopStreamSnapshot`和`applyDesktopDelta`，导入实际`createSnapshotReducer`、runtime缓存、messagesForRender和过程分组。HTTP只重放确认占位，不访问网络或调用发送函数；测试不读取真实会话，不创建模型任务，不操作原权限、队列或网关。

最小失败序列：

1. 实时快照包含`${turnId}-input`临时用户记录，本用例没有clientMessageId。
2. 历史增量到达，包含task_started及同turn、同正文的历史用户记录。合并后暂时只有一份，但历史记录已保存临时nativeMessageId。
3. 下一快照patch明确移除临时ID，并加入带client的正式native用户记录。snapshot reducer结果只含正式记录；App将它与旧runtime列表合并，留下已绑定临时别名的历史项。合并器不再把这条历史项作为未绑定记录，得到两个用户气泡。

将第3步换成完整快照也不能消除旧runtime记录。终稿到达、版本3缓存存取、重连全量和迟到HTTP确认，均未自动修复该构造状态。

48种合法到达顺序（临时快照先于正式快照），覆盖临时/正式client各自有无、历史及HTTP的先后。结果如下，连续3轮完全一致；这只是构造用例分布，不是线上发生率。

| 临时client | 正式client | 用例数 | 出现并保留重复 |
| --- | --- | --- | --- |
| 无 | 无 | 12 | 12 |
| 无 | 有 | 12 | 4 |
| 有 | 无 | 12 | 12 |
| 有 | 有 | 12 | 0 |

- 当前手机隔离测试`pnpm test:mobile`：75/75通过。

- 合成重复写入缓存并恢复后仍为2，草稿和另一条待确认输入保持。

## 建议实施方案（尚未执行）

按同一问题闭环实施，优先修输入临时态，保持发送、引导、排队与审批协议。

1. **明确临时项的退役和继承关系。** 在native快照接入边界识别`turn-input`临时记录被正式原始用户项替换的事实。client一致时直接继承；缺client时必须依赖明确的初始输入替换关系，并检查turn、完整正文和身份冲突。不能把同一turn内所有同文引导都当作初始输入，不能用全文相等全局去重。若现有快照不足以确定关系，再最小补充只读投影的替换元数据；不改变真实控制接口。
2. **让移除与身份迁移一起生效。** App更新时移除已被替代的临时记录；如果历史项已经吸收临时记录，须同步解绑临时native别名并关联正式项。仅按消息id删除无效，因为合并后的id已经可能是log-id；仅扩展文本匹配也无法处理旧别名。保持实际历史、附件、独立client及待确认记录，不能用整个快照覆盖全部runtime消息。
3. **修复现存受影响缓存。** 通过相同的明确替换关系修复已有临时别名，不依赖清缓存。保留草稿、待确认身份/正文、已确认的真实同文输入。对确实缺少证据的旧记录保留并记录诊断，不能猜测删除。
4. **以入口过渡测试作为发布条件。** 将本次48种序列固定为App接入层回归，验证每一步，而不只比较最终数组。增加正式身份补齐、缺页/重复同文引导、两次独立提交、重连、历史分页、缓存、终稿前后及重复快照。浏览器需确认单次始终1个DOM用户气泡、两次真实发送仍2个。最后用新的预览APK完成手机实测，确认任务只收到一次、运行中及重开后均一份，再宣布问题解决。

预期涉及手机App接入、消息合并与runtime缓存及对应测试。若需要网关投影元数据，另补Relay层规范和隔离测试。当前没有必要先重写整个消息系统或删除执行过程展示。

## 为什么此前回归通过

已有回归覆盖了HTTP、历史和正式native的三路顺序，但默认native记录的身份已固定；没有把`${turnId}-input`到正式item的身份变更、snapshot删除、App保留旧runtime以及缓存恢复连成一条测试。

类别是跨层契约与测试覆盖缺口：snapshot reducer正确删除，并不意味着App最终显示列表正确删除。此次补上App接入层的可重复反馈环，后续修正应以它为门槛；当前不将合成失败等同于手机截图根因已完全证明。
