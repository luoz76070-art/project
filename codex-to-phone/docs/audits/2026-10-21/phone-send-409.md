# 手机发送 HTTP 409 排查与修复预览

## 证据与结论

- Broker 日志确认发送和中断路由返回 409；此前手机发送前仍调用 `/api/desktop/active`。历史日志不保存请求正文和响应错误码，因此无法仅凭状态码确定是哪一项校验拒绝。
- 当前原生网关 Tunnel connected。对用户所选会话做只读订阅，收到 120 条消息、有效 native 控制令牌、活动任务 ID，canSend/canInterrupt 均为 true，submission 为 null。检查后关闭新增订阅，没有提交真实消息、答案、审批或中断。
- 正式 APK 更新清单仍指向 18，正式热更新仅兼容 18；旧界面与原生网关不匹配是优先怀疑项。发送时状态变化或控制信息未就绪仍有可能，不能把推断写成已确认根因。
- 源码可复现两个缺口：手机 HTTP helper 丢弃错误响应，只显示 HTTP 409；首次快照尚未到达时，客户端把缺失 capability 当成旧控制方式，可能不带 guard 发送到原生网关。

## 修改

手机启动时一次读取服务状态，依据服务模式及所选会话实时能力共同判断发送条件；旧Relay无需先手动测试连接。控制方式未知、原生令牌缺失、断流、待确认时不发送；只有有效能力才构建 controlToken 和 expectedTurnId（空闲显式 null）。发送路径再次检查当前所选会话，避免等待路由期间切换目标后错发。

原生和浏览器 HTTP 路径均解析已知的 409 错误码，显示控制状态失效、任务变化、提交待确认或标识冲突。未知错误正文不直接显示，不自动重试。仅明确发生在 follower 写入前的两类拒绝可释放匹配的待发标识，供下一次手动发送；已有回执/未知结果继续保留。失败保留草稿及发送期间的新输入。

只修改手机运行逻辑与合成 UI fixture。Mac 网关继续使用已部署的固定版本，没有重启、改协议校验、移除权限或安装宿主插件。
