# 我把 Codex 搬到了手机上

事情是这样的。

我前段时间一直有一个很具体的困扰，我开着 Codex 在电脑上跑一个任务，人一离开电脑，就只能靠猜。

它现在是在读文件，还是在跑测试？

它是不是卡在某个授权弹窗？

它是不是已经把结果写完了，只是我没看到？

更麻烦的是，有时候我在外面突然想到一句新的指令，想让 Codex 继续改，或者让它停一下换个方向。这个时候你会发现，手机能远程看桌面当然是一种办法，但那太重了。

我真正想要的不是远程桌面。

我想要的是一个 Codex 的移动控制台。

电脑继续跑 Codex，手机只负责看进度、发指令、收结果。它不需要把整个屏幕投过来，也不需要保存我所有历史会话，更不需要变成另一个云端聊天机器人。它只需要绑定我正在用的这一台电脑、这一段 Codex 工作流。

于是这个小项目就从这里开始了，名字叫 Mobile Codex，也可以理解成 Codex To Phone。

最早的版本非常朴素。

电脑上启动一个 bridge，生成一个二维码，手机扫码打开网页，然后网页里显示当前 Codex 会话。

这个版本的意义不是好用，而是证明了一件事，Codex Desktop 的会话状态确实可以被抽出来，手机也确实可以看到当前这一轮在发生什么。

但很快问题就来了。

扫码网页太像测试工具了。

Cloudflare Quick Tunnel 的临时地址会变，二维码扫出来一会儿能用，一会儿又不稳定。局域网二维码看起来很方便，但只要人离开办公室，换成蜂窝网络，整条链路就不成立。

这和我一开始的目标是冲突的。

我不是想坐在电脑旁边拿手机看 Codex，我是想离开电脑以后还能知道它在干什么。

然后第二个问题更要命，手机怎么把消息发回电脑上的 Codex？

这里踩了一个挺典型的坑。

我一开始以为，只要在后台启动一个 Codex app-server，恢复同一个 thread，然后把手机消息发进去就行。

理论上很合理。

实际一跑，它确实能生成回复，也确实能写到同一个会话文件里。但电脑当前 Codex Desktop 窗口不会显示这次回复的过程。

这时候我才意识到，问题不是 thread 文件有没有写进去，而是当前 Desktop 窗口有没有参与这一轮执行。

后台跑出来的结果，手机能看见，文件里也有，但桌面 UI 没订阅它，所以你在电脑上看不到那种正在生成的过程。

这就很别扭。

因为我想要的是手机远程控制当前 Codex，而不是在旁边开一个影子 Codex。

后来我把 Mac 端路线切到了一个更直接、也更接近真实用户操作的方法。

先用 `codex://threads/<threadId>` 聚焦目标会话，再通过 macOS 辅助功能，把手机发来的文字粘贴进 Codex Desktop 的输入框并提交。

这个方案听起来没有那么优雅，但它解决了最关键的问题。

消息是从当前 Codex Desktop 窗口发出去的。

所以电脑端能看到输入，能看到回复过程，手机端也能继续同步结果。

当然，它也有代价。

Mac 上需要给 `Mobile Codex Input.app` 辅助功能权限。Codex Desktop 需要能被聚焦，输入框也得能被系统控制。它不是一个完美的后台协议，而是一个工程上足够现实的控制路径。

再往后，浏览器扫码页面被我换成了 Android App。

这一步体验变化很明显。

手机端有自己的 Endpoint 和 Token 配置，有会话列表，有输入框，有附件上传，有主题切换，也有在线更新检查。它不再像一个临时调试页面，而更像一个真的手机工作台。

网络层也换了。

早期的 Quick Tunnel 只适合验证，现在正式方向是 Broker。

Mac Relay 主动连到公网 Broker，Android App 也连到同一个 Broker。这样 Mac 不需要开放端口，手机也不需要和电脑在同一个 Wi-Fi。

链路大概是这样。

Android App 连接公网 Broker。

Mac Relay App 从家里、办公室或者任何网络主动连 Broker。

Broker 只负责转发，不保存完整会话历史，也不变成一个新的 Codex 运行时。

真正读取 Codex、控制 Codex 的，还是那台 Mac。

到现在的 1.1.11 版本，我反而做了一个减法。

之前手机 UI 里会显示工具调用、桥接状态、内部确认、命令输出，甚至有时候还有空白卡片。技术上看起来信息很多，用户体验上就很吵。

因为用户在手机上不是来审代码 diff 的。

他只是想知道，自己刚才发的那句话有没有送到 Codex，Codex 最后给了什么结果，现在有没有还在生成。

所以 1.1.11 把手机界面收敛成两类东西。

用户输入。

Codex 文本输出。

工具调用、完整命令日志、补丁内容、桥接 ack，默认都隐藏。

这不是能力倒退，而是产品边界变清楚了。

手机端是远程控制台，不是桌面端的完整复制。

这一路做下来，我最大的感受是，很多 AI 工具的移动端不是缺一个聊天框，而是缺一个和桌面工作流真正连起来的控制面。

你在电脑上让 Codex 改代码，跑测试，读项目，写文档。这个过程本来就发生在本机环境里。手机如果只是另开一个聊天机器人，它再聪明，也不知道你电脑上正在发生什么。

Mobile Codex 的思路是反过来的。

不让手机变成第二个 Codex。

而是让手机成为当前 Codex 的遥控器。

它现在还不完美。

Mac 输入依赖辅助功能授权，公网 Broker 要自己维护，在线更新还不是应用商店那种丝滑升级，多会话和多设备控制也还没产品化。更底层的 Codex Desktop 协议如果未来能开放稳定入口，这个项目还能继续往前走一大步。

但我觉得这个方向是对的。

因为它解决的是一个真实的小痛点，一个所有重度使用 Codex 的人都会遇到的小痛点。

你不可能一直坐在电脑前。

但你又不想丢掉 Codex 正在推进的那条线。

所以我做了一个手机上的线头。

它不负责取代电脑。

它只是让你离开电脑以后，还能拽住那条正在往前跑的工作流。

说真的，这种感觉还挺爽的。
