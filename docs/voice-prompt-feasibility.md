# 语音输入与提示词整理可行性

2026-10-22分析，10-23更新：用户已选择百炼Qwen-ASR和DeepSeek；源码、APK26及网关本地候选已实现并隔离验证，见[语音输入候选](audits/2026-10-22/voice-input.md)。未部署/安装或调用真实供应商，Key留到手机配置入口联调时填写。以下保留此前分析，候选/目标值不视作真机结果。

## 判断与建议

技术上可行，改造量中等。建议首版采用Android原生录音、云端语音识别、独立文本模型整理、编辑后回填当前会话草稿。Codex和DeepSeek共用输入能力，最终发送仍走各自现有会话控制通道。录音/整理不提交Agent模型任务，也不启动或恢复原线程。

建议流程：点击录音 → 结束录音 → 显示识别原文及整理稿 → 用户采用/修改 → 填入当前会话草稿 → 用户发送。提供“仅转文字”和“整理提示词”两种模式。首版建议单段上限120秒，前台录音；后台/来电/取消的中断必须显式处理。限时、大小、录音格式与成功/取消后的临时文件清理需要真机验证。

## 两种模型能力

语音识别ASR负责保留口述内容，文本LLM负责去口头语、组织要求。普通聊天接口兼容不代表支持音频。两步允许选择不同供应商/密钥；同平台同时提供两种模型时，可在核验地域及权限后复用该平台凭证。

候选语音识别：

- 阿里百炼：当前官方ASR概览提供`qwen-audio-3.1-asr-flash`短音频HTTP识别及`qwen-audio-3.1-asr-flash-message`短语音实时输入。前者支持URL/Base64，适合第一版沿现有JSON通道传有界音频；后者适合后续低延迟迭代。具体模型、地域权限、价格及网络须接入时复核，不预设某个平台网络一定更快。
- OpenAI：当前官方文件转写推荐`gpt-transcribe`，支持M4A等输入及上下文/关键词提示；旧`gpt-4o-*-transcribe`已在官方转写指南标为弃用，不作为新接入默认。文件转写的流式输出与麦克风实时转写是不同协议。

提示词整理可接DeepSeek Chat Completions或所选平台文本模型，配置provider/Base URL/模型/Key。仅适配明确协议的HTTP API，不能把所有“OpenAI兼容”平台当作所有端点均兼容。整理服务的API调用与已有DeepSeek Harness会话桥接分开。

## 提示词的产品契约

“标准提示词”在本项目建议定义为：保留用户意图，短请求保持简短，复杂任务按目标、必要背景、任务范围、约束、交付/验收方式组织。只有原话或用户选定上下文明确提供的事实才作为确定要求；不确定项列为待确认，不猜文件路径、技术栈、执行权限、预算或发布决定。否定、数字、版本、项目名和“暂时只分析”等操作边界必须保留。

示例口述：把手机会话按项目分组，能展开收起，Codex和DeepSeek都要。

示例整理：目标：手机会话按项目分组。范围：Codex和DeepSeek。交互：支持展开/折叠。验收：两类Agent均可分组并操作。待确认：默认展开还是折叠。

采用前保留原文，允许改字/重新整理；整理失败仍可使用原文。用户切换连接、Agent或会话后，迟到结果不得写入另一会话，也不得覆盖整理期间新输入。网络结果未知不自动发送或重复计费重试。首版只在本段语音和用户选择的少量上下文内整理，不默认抓取整个项目或完整会话。

## 对现有工程的影响

- `apps/mobile`目前没有录音插件，AndroidManifest也没有`RECORD_AUDIO`。需增加原生录音插件及运行时权限、录音/识别/整理状态、预览和设置UI；因此首版需要新APK，不能只靠HTML热更新获得原生能力。
- `SecureCredentialsPlugin`目前用于手机连接凭证，采用Android Keystore加密；这不是已经实现了模型Key配置。建议模型长期Key保存在配对Mac的专用凭证存储，由网关代调，手机只显示配置状态/掩码。手机可提供设置入口，但设置接口需有明确配置权限，不能任意配对设备覆盖共享Key。Key不写APK、前端缓存、日志或错误正文。
- `apps/relay`增加独立的语音转写/提示词整理服务与provider适配；不把这些服务写进各Agent适配器。需覆盖鉴权、请求限制、超时/取消、凭证掩码、输出上限和供应商错误归一化。音频作为私有临时输入，不进入通用附件长期存储。
- Broker请求协议`body`为string/null，当前Buffer转UTF-8，不是透明音频二进制隧道。首版短录音可采用有界Base64 JSON，网关再转换供应商要求的multipart或其他格式；保持现有Broker协议。Base64传输体积约增加1/3。后续实时音频需要另行评估有界分块/背压或供应商临时令牌直连，不能把文件转写流当作已经支持实时麦克风输入。

推荐请求路径：手机录音 → 现有鉴权Broker/Tunnel → Mac语音服务 → 语音供应商 → 转写原文 → 文本模型整理 → 手机预览/草稿。模型计算在供应商侧，手机负责编码与UI，Mac负责有界转发和编排；主要延迟变量是网络、音频长度及两次模型调用。该方案依赖Mac网关在线，符合当前手机工作台依赖桌面的使用方式。

系统SpeechRecognizer可作为后续可选入口，但Android要求先检测识别服务是否可用，端侧识别还需检测设备支持情况；不能假设所有手机都有相同识别服务或均可离线。手机直接保存并调用用户Key的BYOK方案可独立评估，但长期密钥在客户端的保护能力弱于后端保管；OpenAI官方明确推荐后端代调。端侧ASR则需增加模型分发、设备性能及电量评估，本次不预设其效果。

## 延迟、费用与验证

建议首版针对10–30秒口述，将停止录音到整理稿可用的目标暂定3–8秒。这是待实测的工程目标，不是当前性能结论。后续如果此目标不能满足，可评估边录边转写以重叠上传/识别时间；不要为每个中间识别片段调用一次整理模型。

费用是转写用量加文本输入/输出Token。按当前GPT-Transcribe公布的0.0045美元/分钟线性估算，累计300分钟转写约1.35美元，另加文本整理、供应商计费粒度与网络费用；这只是可核验的价格参照，不表示默认采用OpenAI。其他供应商要按最终地域/模型计价。

实施前需确认实际可用ASR供应商和提示词模型，并对短中文、夹杂英文/文件名、否定及版本数字做样本对比。验收关注：权限拒绝/取消/来电与后台、真实设备录音、静音/噪音、术语转写、意图保真、超时/断网、草稿和会话隔离、重复操作及费用；只有用户明确发送才进入原Agent会话。首版不包含语音播报、唤醒词、后台持续录音或自动执行语音命令。
