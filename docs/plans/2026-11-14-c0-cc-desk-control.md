# C0：手机控制 CC Desk 会话的接入设计

2026-11-14。对应任务清单 C0，后续 C2、C3、W3b（Claude 部分）、W4b（Claude 部分）按本文执行。

## 结论

- **不需要向上游提 PR。** CC Desk 服务端的 WebSocket 协议本身已经提供会话列表、订阅事件、读历史、发消息、审批与提问回复、停止运行；网关作为一个“只有控制连接、不带执行通道”的客户端直接接入即可，不用在桌面端 Electron 里加 IPC。
- **但当前使用的服务端是 0.3.2（协议 17），只够做只读。** 0.3.2 要求发消息、审批、停止都来自会话所在的那台电脑，而且发起新一轮的连接必须自带执行通道；纯控制连接只能订阅和读历史。上游 0.3.3 起支持“从另一台在线设备操作它的会话”，最新版是 0.3.14（协议 25）。
- 因此推荐：**目标路线 B（服务端升级到 0.3.3 及以上后直连协议）**，在此之前可先上**过渡路线 C（只读 + 定时任务文件发送）**。路线 A（给桌面端加 IPC 的补丁版）只在服务端无法升级、又必须在手机上审批时才考虑。

## 核对到的事实（以服务端源码为准）

| 能力 | 协议消息 | 0.3.2 纯控制连接 | ≥0.3.3 独立设备、纯控制连接 |
| --- | --- | --- | --- |
| 认证 | 首帧 `auth`（协议版本须与服务端完全一致、服务凭据、设备名、`tunnel:false`），随后可发 `device`（设备 ID、系统） | 可以 | 可以 |
| 会话列表 | `ready.sessions`，之后推送 `session.updated` / `session.deleted` | 可以 | 可以 |
| 订阅与历史 | `session.subscribe`（返回快照，之后推送事件）、`session.history` | 可以 | 可以 |
| 发消息 | `message.send`：`requestId` 就是这条消息的 `messageId`，同一 `requestId` 重发不会重复（内容不同报 `request_conflict`） | 不行（要求本连接带执行通道、会话在本设备） | 可以，命令仍在会话所在电脑上执行 |
| 运行中追加 | 同上，进入正在运行的那一轮 | 不行（要求同一设备） | 可以 |
| 审批与提问 | `approval.reply`（`allowed`，提问时带 `answers`） | 不行（要求同一设备） | 可以，两边同时答复时后到的一方收到“已在别处处理” |
| 停止 | `run.cancel` | 不行 | 可以 |
| 新建会话 | `session.create`：会话归属发起连接的设备 | 不适用 | 不适用：归属网关这台“设备”，它没有执行通道，跑不起来 |

补充：

- 每条连接同一时间只订阅一个会话（再次订阅会替换）。
- 事件按会话递增编号：`message.user`、`text.delta`（流式时以片段推送，结束后记成一条）、`tool.requested` / `tool.result`、`approval.requested` / `approval.resolved`、`run.status`（running、awaiting_approval、completed 等）、`run.error`。
- 没有设备标识的旧会话（0.2.11 之前建的）会被第一台对它发消息的 Windows 设备认领；网关必须报告 `platform: darwin`，并且不对没有设备标识的会话发消息。

## 三条路线

| | A：桌面端本地 IPC（补丁版客户端） | B：升级服务端后直连协议 | C：现版本过渡 |
| --- | --- | --- | --- |
| 做法 | 在桌面端主进程加本机 socket（0600，JSON-RPC），借桌面端自己的连接发命令 | 网关以独立设备、纯控制连接接入 | 网关只读接入；发送写桌面端的定时任务文件（一次性任务） |
| 服务端改动 | 无 | 升级到 ≥0.3.3（建议当前最新） | 无 |
| 桌面端改动 | 维护一份基于 0.3.2 的补丁版，自己构建、签名、安装；上游 PR 可选 | 随服务端升级到同版本 | 无 |
| 手机能做的 | 全部 | 全部（新建会话除外，见下） | 看会话和历史；发消息（最多约 1 分钟延迟，消息带“定时任务”标记）；不能审批、不能停止 |
| W4b 回合对应 | 可以（同 B） | 精确：`requestId`=交接的 clientMessageId，`message.user` 所在的那一轮就是消费它的回合，看这一轮的 `run.status` | 做不到精确对应：定时任务发出的消息 ID 不由网关决定，只能做到“送达→进行中”，待验证由用户手动标 |
| 主要代价 | 长期维护 Electron 补丁版 | 服务端升级会重启服务、中断正在运行的会话；协议版本跟随服务端 | 体验打折 |

新建会话（W3b 的 Claude 部分）三条路线都走定时任务文件：`target.type = "new"` 加项目路径，由桌面端建会话并发出第一条消息。

## 网关侧设计（CcDeskAdapter，B 与 C 共用）

- **连接信息**：服务地址和证书指纹取自桌面端已保存的连接设置（不是机密）；服务凭据由用户在电脑上运行一次 `mobile-codex ccdesk login` 输入（不回显），存入系统钥匙串。gateway.json 只记“已登录”，日志与诊断里不出现凭据。证书按指纹校验，没有跳过校验的选项。
- **身份**：网关首次运行生成自己的设备 ID 并保存，设备名“MobiCodex 网关”，`platform: darwin`，`tunnel:false`。不冒用桌面端的设备 ID。
- **版本**：读 `ready.protocolVersion`，按白名单决定能力：17 只开放只读；跨设备操作所在的版本及以上开放写操作。不在白名单时，Agent 列表里显示“CC Desk 版本不受支持（协议 N）”，不尝试连接其他接口。
- **连接数**：每个正在看或正在追踪交接的会话一条连接，最多 4 条，空闲 60 秒关闭；会话列表用一条常驻连接（不订阅会话，只收 `session.updated`）。断线按指数退避重连，用 `session.subscribe` 的 `afterSequence` 补上断线期间的事件。
- **映射到现有 Agent 会话快照**：
  - `message.user` 映射为用户消息，`text.delta` 映射为助手消息，`tool.requested` / `tool.result` 映射为工具消息。
  - `run.status` 映射为会话状态：running 是“进行中”，awaiting_approval 是“等你确认”，completed / failed / cancelled 是本轮结果。
  - `approval.requested` 加上对应的 `tool.requested`，映射为权限请求；Claude 的提问映射为提问卡片。
  - 每轮结果给 S1、活动状态给 S2，沿用现有字段，手机端不需要为 CC Desk 单独改界面。
- **交接与 W4b（路线 B）**：发送时 `requestId` 用交接记录的 clientMessageId。结果不明时用同一 `requestId` 重发，服务端保证不重复。消费回合按 `message.user.messageId` 精确找到 `runId`，这一轮结束时的 `run.status` 决定转“待验证”还是“退回”。
- **路线 C 的发送**：写一次性定时任务（时间取下一分钟），任务 ID 用交接记录 ID，写入前先查重，结果不明不重写。发出后靠只读连接上出现的 `message.user`（文本一致、时间在窗口内）确认送达，只用于显示“已送达”，不用于回合对应。

## 安全与边界

- 只服务同一个人自己的会话，不做多账号、不把订阅转成共享接口，与 CC Desk 自身的边界一致。
- 服务凭据只在钥匙串里；网关进程内存中持有，不写入任何文件、事件或日志。
- 同一服务下的各台设备之间本来就不隔离（CC Desk 安全须知）：网关能操作的范围与桌面端相同，不额外授权。
